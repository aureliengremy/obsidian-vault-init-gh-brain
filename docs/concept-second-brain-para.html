Un [[second brain]] en trois vaults, organisé par actionnabilité

Des notes en Markdown pur, versionnées quand il le faut, synchronisées quand il le faut — et une seule question pour tout classer : « à quel point est-ce actionnable maintenant ? »

Le concept

Pourquoi un second brain

Ton cerveau est fait pour avoir des idées, pas pour les stocker. Un second brain externalise la mémoire : chaque projet, chaque apprentissage, chaque idée d'entraînement vit dans une note atomique, reliée aux autres par des [[liens]]. Le fichier reste du Markdown plat — lisible dans n'importe quel éditeur, exploitable par Git, par Claude Code, par un script. Zéro enfermement propriétaire.

Ce que le système doit te donner concrètement : retrouver une décision prise il y a six mois, reprendre un projet là où tu l'as laissé, et connecter ce que tu apprends à ce que tu construis.

L'architecture

Trois vaults, trois vies, zéro croisement

Chaque vault a son périmètre, son stockage et son mode d'accès. Ils ne se parlent pas — et c'est voulu.

Vault Pro

Laptop professionnel

Projets et mandats professionnels. Dépôt GitHub privé et isolé, commits manuels ou via plugin Git.

  • GitHub privé dédié
  • Pas de sync auto
  • Desktop uniquement
Vault Perso

Laptop personnel

Projets personnels : side-projects, explorations, apprentissage technique. Dépôt GitHub privé et isolé, sans lien avec le vault pro.

  • GitHub privé dédié
  • Pas de sync auto
  • Desktop uniquement
Vault Sync

Vie courante · mobile

Le reste du perso : notes rapides, listes, choses à consulter en déplacement. Synchronisé, accessible sur mobile.

  • Obsidian Sync (ou équiv.)
  • Sync continue
  • Desktop + mobile
Principe d'isolation : aucun remote partagé, aucun sous-module, aucun lien entre les trois. Pas de sync croisée = pas de conflit de merge, pas de fuite pro ↔ perso, et une politique de sécurité simple à respecter côté employeur.
La méthode

PARA : classer par actionnabilité, pas par sujet

PARA (Tiago Forte, Building a Second Brain) ne demande jamais « de quel sujet parle cette note ? » mais « quand vais-je en avoir besoin ? ». Quatre dossiers, ordonnés du plus actionnable au moins actionnable. La même structure se répète à l'identique dans tes deux vaults GitHub.

← actionnable maintenantinactif →
P

Projects

Efforts avec une fin et un objectif. Un projet se termine, se livre, s'archive.
formation-formabois/ tuto-scaler/ site-mariage-clone/
Test : ça a une deadline ou un livrable ? → Projects.
A

Areas

Responsabilités continues, sans fin. On les entretient, on ne les « termine » jamais.
entrainement/ finances/ veille-ia/
Test : un standard à maintenir dans le temps ? → Areas.
R

Resources

Sujets d'intérêt et de référence. Utiles un jour, pour un projet futur ou par curiosité.
biomecanique/ prompting/ livres-notes/
Test : intéressant mais sans engagement ? → Resources.
A

Archives

Tout ce qui est inactif : projets livrés, areas abandonnées, ressources périmées. On n'efface pas, on déplace.
2025-projet-x/ ancienne-veille/
Test : plus d'action prévue ? → Archives.

Le point clé : les notes bougent. Une ressource devient un projet quand tu t'engages dessus ; un projet livré part aux archives ; une area délaissée aussi. PARA est un système de flux, pas un rangement figé.

Le flux

La vie d'une note

Pour éviter que le vault devienne un cimetière : capturer vite, classer plus tard, réviser chaque semaine.

CAPTURE

inbox/

Toute idée atterrit ici en quelques secondes, sans réfléchir au classement.

TRI · HEBDO

Revue

Une fois par semaine : chaque note de l'inbox est classée en P, A ou R — ou supprimée.

USAGE

Lier & enrichir

Les notes se relient par [[wikilinks]] au fil du travail. Le graphe fait émerger les connexions.

FIN DE VIE

Archives

Projet livré ou sujet clos : on déplace, on ne supprime pas. L'historique Git garde le reste.

La structure

Arborescence type & .gitignore

Identique dans les deux vaults GitHub — seule la matière change. La config Obsidian est ignorée par défaut, avec quelques exceptions utiles si tu veux retrouver tes réglages en clonant.

arborescence — vault pro ou perso
vault/
├── 0-inbox/          # capture rapide
├── 1-projects/       # 1 dossier / projet
│   └── mon-projet/
│       └── mon-projet.md
├── 2-areas/          # responsabilités
├── 3-resources/      # références
├── 4-archives/       # inactif, jamais supprimé
├── _templates/       # gabarits de notes
└── _assets/          # images, pièces jointes
.gitignore
# Ignorer la config Obsidian par défaut
.obsidian/*

# … sauf ce qu'on veut retrouver en clonant :
!.obsidian/app.json
!.obsidian/appearance.json
!.obsidian/core-plugins.json
!.obsidian/community-plugins.json

# Jamais versionné : état d'interface volatile
.obsidian/workspace.json
.obsidian/workspace-mobile.json
.trash/
.DS_Store
Les règles

Cinq règles pour que ça tienne

1

Un dépôt privé par vault, .gitignore posé avant la première note. Config ignorée par défaut, exceptions choisies, jamais de token ni de workspace.json versionné.

2

PARA partout, à l'identique. Même squelette dans les deux vaults : le classement devient un réflexe, pas une décision.

3

Notes atomiques et liées. Une idée = une note = des [[liens]]. C'est le graphe qui organise, pas l'arborescence.

4

Commit en fin de session. Une machine par vault : pas besoin de sync, juste un historique propre. Un commit par séance de travail suffit.

5

Inbox + revue hebdo. La capture est instantanée, le tri est un rituel. Sans revue, tout système meurt en trois semaines.
